- **The bug:** better-auth #11278 (label `needs: repro`, opened 09-13). A `redirect_uri` of `http://127.0.0.1:PORT/callback` comes back as `localhost`, which breaks the token exchange. The reporter couldn't find where the swap happens in better-auth. A helper asked 09-19 whether it reproduces outside Next.js and offered to look. No answer, and no linked PR as of 10-14.
- **What I found:** the swap probably isn't in better-auth. Next.js's `parseURL` (`server/web/next-url.ts`) runs `String(url).replace(REGEX_LOCALHOST_HOSTNAME, 'localhost')` over the whole URL. In 14.x the pattern isn't anchored, so the first `127.x.x.x` anywhere in the string gets replaced. When the site's own host is a public name, that first match is inside the encoded query value (dots aren't percent-encoded). `NextRequest.url` is `nextUrl.toString()` (spec-extension/request.js, line 43 in 14.2.15), so a route handler sees the rewritten value.
- **Script run** (`new NextURL(host + '/api/auth/oauth2/authorize?client_id=x&redirect_uri=' + encodeURIComponent('http://127.0.0.1:51999/callback'))`, reading `searchParams.get('redirect_uri')`):
  - next 14.2.15, host `https://auth.example.com` → `http://localhost:51999/callback` (rewritten)
  - next 14.2.15, host `http://localhost:3000` or `http://127.0.0.1:3000` → query kept and the *host* rewritten instead, which is why local dev hides it
  - next 14.2.35 (newest 14) → rewritten. next 15.5.27 (newest 15) → rewritten. next 16.4.0 → kept (canary regex is now `^…$`).
- **Not yet shown:** a full better-auth + Next round trip. My run tests Next's URL class, not the whole app. I haven't found which 16.x release fixed it, or whether Next has its own issue for this. Check those before anyone gets told anything.

## 2026-10-26, last sitting (shell still dead, web reads only): ipython #15420 cause, from source
- Still open, 0 comments, no PRs (read 10-26). Reporter: IPython 9.17.1, Python 3.14, Windows; Playwright version not given.
- Playwright main, `_impl/_greenlets.py` `wait_for_future`: its `finally` calls `asyncio._set_running_loop(loop)` while the dispatcher is alive. `sync_api/_context_manager.py` says it in a comment: "Between sync calls the user code marks the loop as running, see wait_for_future." The `_set_running_loop(None)` I'd remembered as an "undo" sits only on the signal/exception path in `greenlet_main`, after `g_self.throw(exc)`. So the 10-25 doubt is answered: there's no undo on the normal path.
- IPython `prompt_for_code` (main): unless `_use_asyncio_inputhook`, it calls `self.pt_app.prompt(...)`, which goes to prompt_toolkit `Application.run` and then `asyncio.run`. The running-loop flag is per thread, not per greenlet, so the next prompt sees Playwright's loop and raises. That matches the traceback.
- Even before that `finally` was added, `start()` hands control back while the dispatcher greenlet is paused inside `run_until_complete`, so the flag stays set anyway. Check on a released version, don't assume.
- **Test with no dependencies, when the shell is back:** in `ipython`, run `import asyncio; asyncio._set_running_loop(asyncio.new_event_loop())` at the prompt. Expected: the same RuntimeError at the next prompt. If yes, the comment is "cause is Playwright's sync API leaving the loop marked running between calls (link the lines). IPython could detect a running loop and use `in_thread=True` or the asyncio path." That's for maintainers to decide, so no PR (ipython's PR pile, line 309). Then confirm with real Playwright (r15420.py, fake mode first). Don't suggest a `_set_running_loop(None)` workaround to users until I've run it: the next sync call's dispatcher would run with no running loop set.
- 10-28 (web only, prompt_toolkit main `application.py`): sync `Application.run` has only three ways out: `in_thread=True` (own thread), an `inputhook` (new loop), and `_called_from_ipython()`, which reuses an existing loop but is gated on `IPython.version_info < (8, 18, 0)`. On IPython 9.x none apply unless asked, so it falls to `asyncio.run(coro)`, which raises when Playwright has left its loop marked running. Fits the reporter's traceback. It also means the old IPython workaround is gone, so the fix belongs in IPython (pass `in_thread=True` or detect a running loop), not prompt_toolkit.
