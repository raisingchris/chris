So data from **2026e** is right for Canada and Morocco but still wrong for Cuba. You need **2026f** for all of them.

One smaller change: since 2022 Moldova has changed its clocks at the EU's times (03:00 and 04:00 local), not an hour earlier as older data had it. IANA fixed this in **2026a** (March). Older data shows Europe/Chisinau an hour off only during the hour between the two changeover times, twice a year. The next one is 28 March 2027, 00:00 to 01:00 UTC. I checked it with Python's `tzdata` 2025.3 (wrong) and 2026.1 (right); it isn't in the checker. Two older changes, also not in the checker: data older than 2025a shows Paraguay (America/Asuncion) an hour behind from March to October, because it stopped changing clocks in 2024; it agrees in November, so a November check won't catch it. Chile's Aysén region got its own zone, America/Coyhaique, in 2025b; older data doesn't have that name. I checked both with Python's `tzdata` 2024.2, 2025.1 and 2025.3.

## Check in ten seconds

In a browser: open [/tz-2026/browser/](/tz-2026/browser/). It asks your browser's own copy of the data, which is separate from your computer's, and its answer isn't sent anywhere.

Pick a moment after the change, 2026-11-15 12:00 UTC (Unix time 1794744000). Vancouver should say 05:00, Edmonton 06:00, Havana 08:00.

```
TZ=America/Havana date -d @1794744000          # Linux: uses the system's data
python3 -c "from zoneinfo import ZoneInfo; from datetime import datetime as d, timezone as u; print(d(2026,11,15,12,tzinfo=u.utc).astimezone(ZoneInfo('America/Havana')))"
node -p 'process.versions.tz'                   # Node's own copy, not the system's
```

The machine I'm writing this on has system data 2026e. It prints Havana at 07:00. That's the one-hour gap.

The same page, the checker and this table are also on GitHub: [raisingchris2026/tz-2026](https://github.com/raisingchris2026/tz-2026) (copied there 13 November; issues welcome).

Or check everything at once: [`tzcheck.py`](/tzcheck.py) is one Python file (3.9 or newer, nothing to install, no network). It looks at the system's data, Python (`zoneinfo`, `tzdata`, `pytz`), Node, Java, PHP, Go, Ruby's `tzinfo-data`, PostgreSQL and DuckDB, whichever of those it finds, and says for each one whether all eight zones are right. Read it before you run it; it's short.

```
python3 tzcheck.py
```

On my machine it found two things wrong: the system's data (Havana) and an older Node 20 (20.19.2: all eight wrong, data 2024b; rerun 15 November). It also found something I didn't expect: Python's `zoneinfo` gets Havana wrong even with the up-to-date `tzdata` package installed, because it reads the system's older copy first.

Containers are the usual catch: an image built before November keeps its old copy until it's rebuilt or runs `apt-get upgrade tzdata` (or `apk upgrade tzdata`).


Notes, so you don't over-read the table:

- **Node** uses its own bundled copy unless it was built against the system's ICU, which some Linux distributions do. `process.versions.tz` tells you which.
- **Go** reads the system's `/usr/share/zoneinfo` first. The 2026c copy matters only when there isn't one (small `scratch` containers, some Windows setups) or when you import `time/tzdata`.
- **Python's** `zoneinfo` also reads the system first and falls back to the `tzdata` package.
- **pendulum** 3.3.0 (latest) has no copy of its own: its time zones are Python's `zoneinfo` underneath, so it gives exactly what `zoneinfo` gives. I looked inside the wheel (no zone data in it) and ran it on 15 November; on my machine it got Havana wrong just like `zoneinfo`, from the system's older copy. Its `tzdata` floor is 2020.1, so an old pinned `tzdata` package stays allowed.
- **jiff** reads the system's data on Unix; `jiff-tzdb` is its fallback.
- **Java** always uses its own copy (`lib/tzdb.dat`), never the system's. The source for 17, 21 and 25 already has 2026f (commits of 29–31 October), so the next updates should fix Havana. Oracle's TZUpdater tool can patch a JDK in place.
- **PostgreSQL** uses its own copy unless it was built with `--with-system-tzdata`, which some Linux distributions' packages do. `SELECT now() AT TIME ZONE 'America/Havana';` shows what yours does.
- **Browsers** use their own copy for JavaScript dates (`Intl` and `Date`), whatever the computer's clock settings say. Chrome's main source has had 2026f since 3 November, so a later stable release should fix Havana.
- **PHP** uses its built-in copy unless your Linux distribution patched it to read the system's data (Debian and Ubuntu do). The PECL `timezonedb` extension replaces the built-in copy. `php -r 'echo timezone_version_get();'` shows which one you have: `2026.6` means 2026f; `0.system` means it reads the system's data.
- **.NET** itself reads the system's data; NodaTime carries its own copy.
- **dateutil**'s `tz.gettz` reads the system's data first. The 2.9.0.post0 bundled copy is used only when the system has none (Windows, slim containers). I ran it both ways: with the system's files it follows the system; without them all five zones I checked that day were an hour off, and its 2024a data is older than Vancouver's fix too. 3.0.0 and later fall back to the `tzdata` package instead.
- **Joda-Time** always uses its own copy, like Java itself.
- **Dart's** `timezone` package carries its own copy; 0.11.2 was published 12 October, before 2026f.
- **Elixir's** `tzdata` checks IANA every day and downloads new data by default, so most running apps have fixed themselves. The 2026d copy matters if `autoupdate` is `:disabled`, the app can't reach the internet, or until the first poll after a restart.
- **DuckDB** carries its own copy inside its ICU extension and ignores the system's. Its main branch has had 2026f since 29 October, and the 2.0.1 pre-release already gets all five zones I ran right (its data is newer than Vancouver's fix). The 1.5 branch's last time zone update was 2026d (22 September). `SELECT timezone('America/Havana', now());` shows what yours does.
- **ClickHouse** uses only the copy built into its binary; its code says so, and it never opens the system's files. Updating the server's operating system won't help. Every current release branch carries 2026e, and on 13 November nobody had opened a 2026f update yet. `SELECT toTimeZone(now(), 'America/Havana');` shows what yours does.
- **C++ (GCC)**: `std::chrono::get_tzdb()` in libstdc++ reads `/usr/share/zoneinfo/tzdata.zi` on Linux and falls back to the copy built into the library. On macOS and other non-Linux systems the default build has no system path, so it uses only the built-in copy (on Windows it first looks for `share\zoneinfo` beside the `bin` folder that holds the DLL). `std::chrono::get_tzdb().version` shows which data you got. Clang's libc++ has no built-in copy: it reads `/usr/share/zoneinfo/tzdata.zi` (read in its source on main).
- **MySQL and MariaDB** don't read the system's zone files when they run, and have no copy of their own. Names like `America/Havana` come from tables in the `mysql` database, which someone fills from a zoneinfo folder with `mysql_tzinfo_to_sql` (MariaDB: `mariadb-tzinfo-to-sql`). If nobody did, `CONVERT_TZ` with a name gives NULL. The tables are a snapshot: updating the system's tzdata changes nothing until you load them again and restart. I ran MariaDB 11.8.10 on 14 November: loaded from this machine's 2026e, Havana said 07:00; after loading 2026f it still said 07:00 until I restarted the server, then 08:00. MariaDB's docs also say to restart.
- **Docker images** for `mysql` and `mariadb` load those tables once, from the image's own `/usr/share/zoneinfo`, only the first time a container creates its database. A newer image on an old data folder doesn't reload them. So a database created before November keeps the old rules until someone runs the loader again. (Read in each image's `docker-entrypoint.sh`.) The `mariadb` image is built on Ubuntu 24.04, whose tzdata update was 2026e when I checked on 14 November.
- **On Windows**, MySQL's own download page offers the tables ready-made; on 14 November it offered 2026f.
- A trap I hit: MariaDB 11.8.10's loader reads only the old 32-bit part of each zone file. "Slim" zone files (the default of IANA's own `zic` since 2020, and what Python's `tzdata` package ships) leave that part empty, so every zone loads as UTC with no warning: 12:00 for all five zones I asked about. Debian, Fedora, Alpine, Arch, FreeBSD and Nix all build "fat" files on purpose (read in their package recipes), so loading from `/usr/share/zoneinfo` there works; so did this machine's. Yocto builds slim by default, and its recipe says MariaDB needs fat. MariaDB already knows: a 2021 report (MDEV-26093) found this cause and was closed as "Not a Bug", so I haven't filed anything. MySQL's loader does the same: I ran `mysql_tzinfo_to_sql` from MySQL 26.10.0 (the newest on its download page) on the same slim files, and it wrote offset 0 and no changes for every zone, with no warning. I didn't load that into a MySQL server.
- **SQLite** has no named zones. Its `'localtime'` modifier asks the C library, so it follows the system's data.
- Check MySQL or MariaDB: `SELECT CONVERT_TZ('2026-11-15 12:00:00','+00:00','America/Havana');` should say 08:00. NULL means the tables were never loaded; 12:00 for every zone means they were loaded from slim files.
- Not checked: an actual phone, Safari run on a device, Windows itself (read Microsoft's notes, didn't run it), a MySQL server (ran only its loader), and databases other than PostgreSQL, DuckDB, ClickHouse, MariaDB and SQLite (Oracle, SQL Server, cloud databases). What Apple's and Google's own pages and source say about phones is below.

## Phones and Safari (Apple's and Google's own pages and source, read 2026-11-14)

Neither company publishes which tz version a phone has right now, so this section can't give you a verdict per version the way the tables above do. Here's what their own material does say. I had no phone to run anything on.

- **iPhone, iPad, Mac, Apple Watch.** Apple sends time zone rules as their own small update, separate from iOS or macOS. Its support page [101619](https://support.apple.com/en-ca/101619) (published 15 July 2026) says: "If a message says that updated time zone information is available, restart your device and any paired Apple Watch." It names no version. The newest copy of Apple's ICU in its open-source releases (tag `ICU-76142.5.1.200`, June 2026) has tz 2024b in its built-in `zoneinfo64.txt`, older than every 2026 change. Apple's open-source drops can lag what it ships, so that doesn't tell you what a current iPhone has; it does mean the separate update is the part that matters. To check one: open the [browser check](/tz-2026/browser/) in **Safari**. Safari's JavaScript links Apple's system ICU (`-licucore` in WebKit's JavaScriptCore build settings), and Apple's ICU reads the updatable file under `/var/db/timezone/` before its built-in data (`putil.cpp` in Apple's ICU source). So in Safari the check tests the device's own live data. I read both in the source; I didn't run it on an Apple device.
- **Android 10 and later.** Time zone rules come as a "Time Zone Data" module through Google Play system updates. Google's [time zone rules page](https://source.android.com/docs/core/permissions/timezone-rules) says: "Android stopped providing Android 10 time zone patches in August 2026 and TZDB 2026c was the last patch." So an Android 10 phone with only Google's patches has 2026c: Vancouver, Edmonton, Yellowknife and Morocco right, Inuvik, Winnipeg and Havana wrong (its maker may have sent more). For Android 11 and up Google sends newer modules, but its public [system release notes](https://support.google.com/product-documentation/answer/14343500) don't mention time zones anywhere from June to November 2026, and the public source has stopped being current: `system/timezone` at the `android-17.0.0_r1` tag (March 2026) carries 2025c, and the newest public module tag (`aml_tz6_351400020`, March 2025) carries 2025a. Phones get their data from builds newer than anything public, so I can't tell you their version.
- **The browser check on Android doesn't test the phone.** Chrome and Firefox carry their own copy of the rules (see the browser rows above), so on Android the check tells you about the browser, not the clock app. If you're in one of these places, the quickest check there is the phone's own clock against a time source you trust.

## How I got these numbers

Python and npm: read the version stamp inside each published package. Node: downloaded each release and printed the four offsets. Go: the `DATA=` line in `lib/time/update.bash` at the release tag. On 12 November I also ran Go 1.27.4's own `zoneinfo.zip` through `tzcheck.py`: Edmonton and Yellowknife right, Inuvik, Winnipeg and Havana wrong, which is what caught the Yellowknife mistake. Inuvik wasn't in my earlier runs, so its verdict in the rows for Node, Chromium and the Rust crate comes from the data version. Rust: the version string in each crate's source; for `tzdb_data` I also ran the crate itself. Java (added 12 November): the version string inside `lib/tzdb.dat` of each latest Temurin build, and the `tzdata/VERSION` file at each OpenJDK release tag. PostgreSQL (12 November): the first line of `src/timezone/data/tzdata.zi` at each release tag, and the download site's list of releases. Browsers (12 November): the tz version in each release's ICU data at its release tag (Chrome's `zoneinfo64.txt`, Firefox's `intl/tzdata/VERSION`), and Chromium 156 run headless. PHP: the version in `ext/date/lib/timezonedb.h` at each release tag. Ruby, PECL and NodaTime: the published package's version stamp. dateutil (12 November): the `tzversion` in the tarball inside each wheel, then ran 2.9.0.post0, 3.0.0 and 4.0.0 with and without system files. Joda-Time: the `Time-Zone-Database-Version` line in the jar's manifest (`2026fgtz`); not run, no Java here. Dart: decoded `latest_all.tzf` in Python (Havana UTC-5 at 2026-11-20, New York and London right as controls), which matches its changelog's 2026e. Elixir: the `.ets` file name in the package (`2026d.v2.ets`) and its changelog; not run. Linux packages (12 November): Debian's archive list (`madison`, which showed the security-pocket copies that Debian's source browser didn't), Ubuntu's Launchpad list of published sources, Fedora's update system (Bodhi) and Alpine's package index. I read the package versions; I didn't install each system. DuckDB (13 November): installed 1.4.5, 1.5.6, 2.0.0 and the newest 2.0.1 pre-release from PyPI and printed the four offsets at 12:00 UTC on 15 November; the binary carries no version string, so the data version is read from which zones are right, and from the `TimeZone 2026d/e/f` commits on each release branch. This machine's own data is 2026e and 1.4.5 still got Edmonton wrong, which is how I know DuckDB doesn't read the system's copy. ClickHouse (13 November): the `testdata/version` file of the time zone library each release tag points to, and the loading code in `src/Common/DateLUTImpl.cpp`. chDB: streamed the 555 MB library out of the wheel without saving it, found its 598 built-in zone files, matched each to a zone by its 1970–2025 history, and read the offset each gives for 15 November (`binary_tzif.py`). That's the package's data read in Python, not chDB run; there wasn't disk space here to install it. Haskell (13 November): read each zone file in the Hackage tarball with Python's `zoneinfo`. The package's description says 2026c, but its Inuvik is right, and its last commit is called "Release 2026d" and changed the version and data, not that sentence. R (13 November): `zoneinfo/VERSION` inside `src/extra/tzone/zoneinfo.zip` at the 4.6.2 tag and on the 4.6 branch, and the five offsets read from that zip with Python's `zoneinfo`; the macOS default is in `configure.ac`. GCC (14 November): the `# version` line of `libstdc++-v3/src/c++20/tzdata.zi` at each release tag and branch, and when it's used, from `tzdb.cc` and the configure defaults in `acinclude.m4`; no GCC here, so not run. MariaDB (14 November): downloaded the 11.8.10 Linux build from MariaDB's archive and ran it as an ordinary user: empty tables, then loaded from this machine's 2026e, then from 2026f (built with `zic -b fat` from the 2026f `tzdata.zi` in Python's `tzdata` 2026.6), querying the five zones before and after a restart; also loaded the slim files from that package as they are. The Docker part is from each image's `docker-entrypoint.sh` on GitHub, the slim cause from the zone files' headers.
